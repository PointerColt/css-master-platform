Chapter 2: The Cascade, Specificity, and Inheritance

Topic 2.1: The CSS Cascade

Welcome to Chapter 2! Up to this point, you have learned how to set up your workspace, write basic style rules, and link stylesheets to your HTML. But as your websites grow, you will quickly run into a major question: What happens when multiple CSS rules target the same element and try to apply conflicting styles?

The browser doesn't crash, and it doesn't make a random guess. Instead, it relies on a beautiful, mathematical sorting engine called the Cascade.

What is the Cascade?

To understand the Cascade, let's use a real-world analogy.

Imagine you are a builder building a new house, and you are trying to decide what color to paint the front door. You receive instructions from three different people:

  1. The City Building Code says: "All doors in this neighborhood must default to white."
  2. The Homeowner says: "I want my door to be painted navy blue."
  3. The Homeowner (shouting in an emergency) says: "Actually, paint it bright red so emergency workers can find it!"

To resolve these conflicting instructions, you follow a strict chain of command. You automatically ignore the city code because the homeowner has a higher say. And you ignore the homeowner's first request because their emergency shout takes ultimate priority.

In CSS, the browser does the exact same thing. The Cascade is a series of four cascading filters that your styles flow through. only the styles that survive every single filter are actually painted on the element.

The Four Cascading Filters

When a conflict occurs, the browser runs the styles through these four steps, in order:

1

Match Check

Filter out rules that don't target this element

2

Origin & Importance

Compare normal vs. !important rules. !important wins.

3

Specificity

Tie-breaker: Most specific selector wins

4

Source order

Tie-breaker: Last rule written wins

Let's break down each step in detail

Step 1: Match Check

The browser scans all stylesheets (browser defaults, linked stylesheets, and inline attributes) and finds every single rule that matches the target element. Any rule that doesn't target the element is filtered out.

Step 2: Origin & Importance

Not all style instructions carry the same authority. The browser groups the matching rules into five distinct levels of priority based on where they came from (Origin) and how urgent they are (Importance):

Priority Level Origin & Importance Type Explanation
1 (Highest) Reader !important Custom accessibility styles set by the user marked with !important.
2 Author !important Styles written by you (the developer) marked with !important.
3 Author Normal Your standard CSS rules and styles.
4 Reader Normal Standard settings set by the user in their browser preferences.
5 (lowest) User Agent Defaults The browser's built-in default styles (like blue links or bold headings).

What is !important?

If you want to override the normal cascade hierarchy, you can append the keyword !important to the end of any CSS value. This acts like "shouting" to the browser, raising that single declaration's weight up to a higher tier.

CSS
/* An Author Normal declaration */
p {
    color: gray;
}

/* An Author Important declaration (wins the origin battle!) */
p {
    color: red !important;
}

Step 3: Specificity

If conflicting rules exist within the same origin level (for example, two developer-written rules), the browser uses Specificity to break the tie.

The rule carrying the more specific selector wins, regardless of where it is written.

  • An ID Selector (#featured) is highly specific (0,1,0,0).
  • A Class Selector (.highlight) is moderately specific (0,0,1,0).
  • An Element Selector (p) is very generic (0,0,0,1).
CSS
/* Class Selector (Specificity: 0,0,1,0) - WINS! */
.highlight {
    color: blue;
}

/* Element Selector (Specificity: 0,0,0,1) - LOSES */
p {
    color: red;
}

Even if the paragraph selector is written last, the class selector wins because it is more specific.

Step 4: Source Order

If the browser evaluates origin, importance, and specificity, and still finds a perfect tie, it uses Source Order as its final tie-breaker: the rule written later in the document wins.

CSS
/* Class Selector (Specificity: 0,0,1,0) - WINS! */
.highlight {
    color: blue;
}

/* Element Selector (Specificity: 0,0,0,1) - LOSES */
p {
    color: red;
}
Common Mistake

Mistake 1

The Scattered Selector Trap:

Avoid styling the exact same element selector in different places across your stylesheet. Writing h1 rules on line 10, line 50, and line 200 splits up your thoughts and leads to conflicting styles that are incredibly hard to trace. Keep all declarations for a selector grouped together in a single rule set.

Mistake 2

The "Later is Always Better" Myth:

Do not assume a style will win just because you wrote it at the bottom of your CSS file. Remember, Source Order is only used if Specificity is a tie. A class selector at the very top of your file will always defeat an element selector at the bottom.

Mistake 3

The Shorthand property Overkill:

If you append !important to a shorthand property like background: blue !important;, you are applying !important to every background sub-property (color, image, repeat, positioning) simultaneously. This can cause unexpected layout bugs because you cannot easily overwrite those sub-properties later.
